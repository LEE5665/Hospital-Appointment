# 검사·처치 요청과 기록 조회

## 화면 흐름

1. 의사가 진료를 시작하고 진료 화면의 `검사 · 처치 요청 및 결과`를 펼칩니다.
2. `새 검사·처치 요청`에서 검사/처치 분류를 선택하고 항목명과 요청 사항을 직접 입력해 등록합니다.
3. 왼쪽 메뉴의 진료 관리 바로 아래 `검사 · 처치`에서 수행 대기를 조회합니다.
4. 의사 또는 간호사가 요청을 선택해 수행을 시작하고 결과/수행 내용을 입력한 뒤 완료합니다.
5. 요청 의사가 완료 결과를 읽고 `의사 결과 확인`을 누릅니다. 확인자와 확인 시각을 저장합니다.

진료 화면에는 기본적으로 이번 진료의 요청만 표시됩니다. `이 환자의 과거 기록 포함`을 선택하고
조회하면 다른 방문의 검사·처치 기록도 최신 요청순으로 확인할 수 있습니다.
`해당 진료 열기`로 해당 방문의 SOAP, 진단, 처방을 함께 확인합니다.
별도 메뉴에서는 요청일·유형·상태·내 요청·완료 미확인 필터와 50건 단위 페이지를 제공합니다.
요청일을 비우면 모든 날짜를 포함합니다. 초기 수행 대기는 날짜 제한 없이 보여주므로 이전 날짜의
미완료 요청을 놓치지 않습니다. 결과는 자동 갱신이 아니라 조회/새로고침 기준입니다.

## 저장 구조와 권한

- `order_items`: 항목 기준 정보(내부 코드, 이름, TEST/PROCEDURE 구분, 활성 여부).
  직접 입력한 이름과 유형에 일치하는 활성 항목을 재사용하고, 없으면 내부 코드로 생성합니다.
- `clinical_orders`: 독립 엔티티. 진료 및 선택 항목 참조, 요청 당시 항목명/유형,
  요청 의사/내용/시각, 상태, 수행자/시작/완료 시각, 결과, 취소 사유/시각, 결과 확인자/시각, version.
- 진행 중인 진료의 담당 의사만 요청할 수 있습니다. 요청 의사만 수행 전 취소할 수 있습니다.
- 의사 또는 간호사가 수행 시작할 수 있으며 시작한 담당자만 완료할 수 있습니다. 관리자는 조회만 합니다.
- 상태는 REQUESTED → IN_PROGRESS → COMPLETED, 또는 REQUESTED → CANCELLED입니다.
- 완료 결과는 수정·삭제할 수 없습니다. 요청 의사만 결과를 확인 처리할 수 있습니다.
- 진료가 완료되어도 기존 요청의 수행·완료·결과 확인은 가능합니다. 새로운 요청은 불가능합니다.
- 오더의 독립적인 version과 DB 행 잠금으로 중복 수행, 오래된 요청, 동시 상태 변경을 막습니다.
- SOAP/처방과 독립적으로 저장하므로 수행자가 결과를 기록해도 의사의 SOAP/처방을 덮어쓰지 않습니다.
- 입력 중에는 목록 전환/새로고침을 제한합니다. 저장 실패 시 초안을 유지하며 `입력 취소`로 폐기할 수 있습니다.

## 최초 항목

`OrderItemInitializer`가 목록이 비어 있을 때 검사 4개(CBC, 소변검사, 흉부 X선, 심전도),
처치 3개(드레싱, 상처 세척, 봉합사 제거)를 등록합니다. `LOCAL-` 코드는 프로젝트 내부 예시이며
공식 검사/처치 청구 코드가 아닙니다. 기존 항목은 덮어쓰지 않습니다.
현재 결과는 텍스트 요약입니다. 파일 첨부, 검사 수치별 결과, 정정 이력, 검사 장비 연동은 포함하지 않습니다.
투약 요청 기능은 추가하지 않습니다.

## API

- `GET /api/clinic/orders/items`: 활성 항목.
- `POST /api/clinic/orders`: `{encounterId, type, itemName, instructions}`.
  기존 `{encounterId, itemId, instructions}` 요청도 호환됩니다.
- `GET /api/clinic/orders`: `date`, `encounterId`, `patientId`, `type`, `status`, `mine`, `unreviewed`, `page`로 조회.
- `POST /api/clinic/orders/{id}/start|complete|cancel|review`: `{version, text}`.
  complete의 text는 결과/수행 내용, cancel의 text는 취소 사유입니다. start/review는 빈 문자열을 보냅니다.

서버 재시작 시 Hibernate가 새 테이블을 생성하고 초기 항목을 등록합니다.
